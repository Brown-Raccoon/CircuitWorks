# **1. Description**  
CircuitWorks is a 2Dgame that aims to teach players how to create circuits and program with them. Players can expect to find 
themselves in a dynamically generated world envionrment so that each player will have a world unique to them. Players will 
also be able to customize their character adding more personality to the way they play. Additionally, progress made in the game will be saved. 
Saving progress means that players will not have to worry their hard work will disapear. Instead, players can seamlessly continue
where they left off.  
  
CircuitWorks implements these features through several different ways. One way is by creating a clear, understandable UI when 
a user interacts with a feature. For example, to create a world players will be shown a UI with options to input a name, world seed
(used for dynamic world generation), and a difficulty setting. This gives players a easy way to get straight into the game without
needing to navigate a complex interface. Another example is seen in the world generation. The world generation is made through the 
random selection of different tiles. These tiles correspond to different envrionment types which are present when a player enters
the word.  

# **2. Architecture**  
<img width="1605" height="608" alt="umlcircuit" src="https://github.com/user-attachments/assets/ef5f8328-855c-4010-8852-404c825e7966" />

CircuitWorks employs a layered approach where user interface, game logic, and data storage are separated. The Presentation Layer includes the menu and game controls, including the world and character creators and the game inventories. This layer allows players to create their own worlds, load game worlds, and customize their characters. The main game functionality, CircuitWorks, sits in the Game Logic Layer. Modules here are for world generation, characters, inventory, placing machines and belts, and the placement of resource nodes in the world. Save handler, the persistence layer, creates, loads and saves the game data to enable players to save their progress. Other game data, including game configuration, and biome and item information is stored as JSON files. Images of characters and the game saves also exist outside the main program. The organization of CircuitWorks provides flexibility and makes the code easy to understand and maintain. The separation of the code also means each feature can be modified without changing unrelated code. One limitation of the current implementation is that the layers are not completely independent. In a future version, these modules could be reorganized to reduce dependencies and make the architecture more independent.

**Quality Attributes**
- Maintainability: Features are partitioned across modules. As a result, code for each feature is located and modified in one place.
- Reusability: Character and inventory logic and machine placement logic have all been implemented in their own modules. Thus, this functionality can be easily shared by other parts of the system.
- Modifiability: In game data is changed by modifying the JSON configuration files, avoiding any modifications to the Python code.
- Testability: In-game logic and UI code are partitioned into separate modules to support testing of each feature.

**Alternative**
- Alternatively, the majority of functions of the program could have been included in one large file that contains Python code. This can be advantageous since the project will be easy to begin because all the code will be located in one place. On the other hand, it becomes more difficult as the program called CircuitWorks becomes more complex to maintain and test.

# **6. Design Principles**  

## Encapsulation ##

Encapsulation keeps the Data and Code that works with it in one spot. Code outside of this capsule can't just enter and affect it.
It has to ask through public functions. For example, in [inventory.py](https://github.com/Brown-Raccoon/CircuitWorks/blob/main/inventory.py)
self.items are kept in the Inventory class. This prevents us from setting other code from accidently interfering with the inventory system. 
This also allows outside code to still work if we break something inside inventory.

This is beneficial because if we mess up something inside of inventory world_generation.py and character_creator.py can still work


## Don't Repeat Yourself ##

Don't Repeat Yourself allows code to reuse a part to prevent unnecessary copies of the same code through the program. For example, instead of
programming each belt tile to be drawn when placed, we have a [Belts.json](https://github.com/Brown-Raccoon/CircuitWorks/blob/main/Belts.json) 
that the program reads how the belt should look. All belts facing the same orientation look the same because they are reusing the same design 
from the JSON. Instead of coding in 10 copies of the json file to draw 10 belts, its one JSON file being reused.

This is beneficial because if we don't have to make changes or bug fixes to 10 copies to fix all 10 belts. We have one that we change/fix and
all 10 belts are fixed.
