# System Description



Circuit Works serves to address **Player** general electronic knowledge, critical thinking, and engineering mentalities by transforming abstract concepts - such as resource flow, logic circuits, power transformation, product efficiency, and scientific experimentation into interactive, hands-on gameplay. Design infrastructure and how **Players** interact with them incentivize the development of these skills and knowledge. The circuit and logic design system invite creative solutions to power transformation and automated controls, whilst the ever-growing end goal calls for larger inventories and efficient logistics and rewards players with a satisfying result, the more efficient the more satifing. The core gameplay loop heavily rewards players who develop these skills, in most way by developing these skills further.

# Conceptual Model

In this section, include the conceptual model of your system as a UML class diagram.

Minimum Requirements:

At least 8 classes (if you need more classes, you can add requirements that did not appear in D2)

Strictly use UML syntax

What TO Include:

Classes

Attributes for each class (no data types needed)

Associations with their multiplicities (1, 0..1, 1.., 0.., etc.) and names

Compositions, aggregations, and inheritances where appropriate

UML comments for complex decisions

What NOT to Include:

UI elements (menus, buttons, screens, pages)

Technical implementation details (databases, servers, libraries)

"System" as a class

Actions that do not need to be persisted

Arrows on regular associations (they indicate directionality, which is not relevant for a conceptual model)

Unnecessary inheritance or complexity

Design Principles:

Maintain simplicity and clarity

Ensure high cohesion within classes

Minimize coupling between classes

Use appropriate abstraction levels

Avoid unnecessary repetition

 Some points to consider:

Use UML adequately. Do not include graphical elements that are not part of the language. 

Do not include an ER diagram (entity-relationship model), which is focused on relational database systems. 

Do not overcomplicate how you represent the elements of your model (e.g., using inheritance or an association when they are not necessary). 

Do not represent technical elements, such as user interface or programming language libraries. At this point, we are modeling the business logic/domain of your system. The model will be refined during the design phase to include technology-specific elements and decisions. UI elements like pages are not concepts that should be in the conceptual model.

Do not represent "System" as a class in your model. Everything you are modeling is part of the system.

Include the multiplicity and the names for all associations.

Use object-oriented (OO) modeling even if it is not used in the implementation. The goal of this phase is conceptual modeling, which is independent of the implementation.

Focus on classes and attributes; methods are not needed at this stage.
