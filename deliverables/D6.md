# **1. Introduction**  
**Description**  
CircuitWorks is a 2D gamed based off factory simulation and automation. The game will also be brought to players as a way to learn these concepts. The game includes dynamic world generation alongside a new addition of biomes. World generation and biomes combine to create unique worlds. Biomes also serve as a way to engage the player and their environment while exploring for resources. Since the previous version, besides biomes, players can now place machines anywhere in their world. This gameplay element provides for a more engaged player experience when creating their own machines to customize or play however they like. Most important, players can save their progress. Saving allows players to make progress then continue without needing to restart.  

**Value proposition:**  
CircuitWorks aims to provide players with the fundamentals and knowledge of computer science, engineering, and insutrial automation in a fun game enviornment players can explore on their own.  

**MVP:**  
The main features in this MVP are game saves, larger world size, dynamic world generation, machine placement, world biomes, and player inventory. New additions to the MVP are larger world sizes, world biomes, and player inventory. Biomes are unique enviornments in the world that a player can explore, similar to real life envionrments/locations. Players are still able to collect resources in these new biomes. Players can also place machines in the world. Larger world sizes allows the player to more freely exploer the world. Players may choose to build near a biome they like or collect resources in a certain biome. Player inventory will allow them to track, manage, and place their machines. An inventory is very helpful so that players can have an easy way to access the items they have collected.

# **6. Retrospective Analysis**  
**1. Key Learnings:**  
As a team, we learned to work together on a software project. GitHub is an amazing tool that allowed us to easily check in with each other to see what additions are made. Weekly meetings provided a solid strucuture to check in with each other and plan what should be done next. Everyone in the group learned how to use the library PyGame to make the project which improved each members skill using Python. Each memeber learned about UML diagrams, key steps of the lifecycle of a project, software testing, and defining requirements for a new project beyond simply just coding.  

**2. Challenges Overcome:**  
One challenge we faced was making sure each group member was able to attend the weekly meetings. This was mostly solved but not completley due to life situations out of our control. The team originally had availability on Firdays but was moved to Sundays to accomadate more members. Weekly meetings switched from those two days when availability was best.  
Another challenge was through GitHub itself. We had difficulty keeping each members additions from breaking or imporoperly being merged into what has been done. This was solved by learning the process of how GitHub makes pull requests. We learned that every file changed will be addded when making a pull request. This was solved by making changes to only 1 file at a time and/or by making new branches for new features that are being worked on such as a deliverable branch. Likely the biggest challenge was working with PyGame for the first time. Everyone was familiar with Python but not PyGame. Video tutorials and reading PyGame docs helped build our understanding as time went on.  

**3. Future Improvements:**  
Communcation and team meetings  
   - **Process:**  
      The biggest area of improvement is in communication and weekly meetings. As stated before, Fridays and Sundays were the days most memebers could attend but sometimes were unable to. Attendance can be improved by finding a new time/hour that worked better than last weeks since schedule changes or life events sometimes occur. Communication is something to be someewhat improved. Rather than saving everything that is needed to be talked about for meetings we should update progress or roadblocks during development within the week. The process for this can be a small check in during the middle of the week in which each memeber talks about their experience without needing to directly set up meeting with a time block that requires everyone to participate.
